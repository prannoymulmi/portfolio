# Phase 1 Data Model: pnpm Migration

This feature has no runtime data model — it changes build/install tooling, not
application data. What follows is the inventory of on-disk **configuration
artifacts** the feature spec's Key Entities map onto, standing in for the usual
entity/field list.

## Lockfile

| Before | After |
|---|---|
| `package-lock.json` (npm, committed) | `pnpm-lock.yaml` (pnpm, committed) |

- **Lifecycle**: `pnpm-lock.yaml` is generated by the first `pnpm install` against
  the existing `package.json` (no dependency version changes — this migration does
  not bump any package). `package-lock.json` is deleted once `pnpm-lock.yaml` is
  verified to produce a working install (FR-002).
- **Invariant**: Exactly one lockfile exists in the repo root at any time after the
  migration lands. Two lockfiles present simultaneously is the failure mode Edge
  Case 1 in the spec describes (a stray `npm install` regenerating
  `package-lock.json`).

## Package manifest (`package.json`)

- **New field**: `"packageManager": "pnpm@11.22.0"` (Corepack pin — research.md
  decision #2). No other field changes; all existing `scripts` entries keep their
  current names and behavior (FR-006).

## CI workflow (`.github/workflows/ci.yml`)

- **Changed steps**: add `pnpm/action-setup@v4`; change `actions/setup-node@v4`'s
  `cache: npm` → `cache: pnpm`; change the install `run:` line from
  `npm ci --legacy-peer-deps` to `pnpm install --frozen-lockfile`; change every
  `npm run <script>` invocation later in the workflow to `pnpm run <script>` (or
  `pnpm <script>` for scripts pnpm exposes directly).

## Deployment config (`vercel.json`)

- **Changed field**: `installCommand`: `"npm install --legacy-peer-deps"` →
  `"pnpm install"` (FR-010, research.md decision #4).

## Documentation artifacts

| File | What changes |
|---|---|
| `README.md` | Quick Start command table, Deployment section's install-command mention |
| `CONTRIBUTING.md` | Setup steps, pre-push checklist, any example `npm` command text |

## Governance artifacts

| File | What changes |
|---|---|
| `.specify/memory/constitution.md` | Principle IV's Deployment bullet: replace the `--legacy-peer-deps`/npm sentence with the pnpm equivalent; version bump (MINOR, per Governance's semantic-versioning rule for a Principle IV substitution) and a `SYNC IMPACT REPORT` entry, following the pattern of the existing amendment history at the top of the file |
| `docs/adr/` | New ADR (next sequential number after 0021) recording the npm→pnpm decision, following the format of ADR 0021 (Status/Date/Amends-or-related header, Context, Decision, Consequences) |

No entity has a state machine, relationships to other entities, or validation
rules beyond "exactly one of {`package-lock.json`, `pnpm-lock.yaml`} exists" — this
is a configuration swap, not a data feature.
